# Sub2API v0.1.150 定制版升级设计

## 目标

将当前基于官方 `v0.1.149` 的 Sub2API 定制版升级到官方 `v0.1.150`，保留现有充值页、自定义菜单、排行榜入口和内嵌前端行为，构建 `sub2api-custom:0.1.150-ui1`，部署到现有生产服务器，并完成本地与线上验证。

完成标准：

- 定制主仓库包含官方 `v0.1.150` 的全部改动。
- `/recharge`、自定义菜单、支付站点 iframe、排行榜 iframe 和登录保护继续工作。
- 官方 `v0.1.150` 新增的公共设置路由保护、GPT-5.6、compact/SSE、计费并发及支付恢复改动不被定制代码覆盖。
- 本地相关测试、前端全量测试、类型检查、生产构建和 Linux amd64 后端构建通过。
- 生产环境只替换 `sub2api` 应用容器；PostgreSQL、Redis 和排行榜容器不重建。
- 线上健康检查、页面、安全头和排行榜契约通过；否则恢复 `0.1.149-ui1`。

## 方案选择

采用在升级分支上对官方标签执行 `--no-ff` 合并的方案。

选择理由：

- 当前仓库已经使用相同方式合并 `v0.1.149`，符合现有历史。
- Git 可自动合并绝大多数官方改动，并把真正的双边修改集中在路由文件。
- 官方提交和本地定制提交均保留，便于审计、回滚和下一次升级。
- 相比从目标标签重新挑选定制提交，遗漏 CSP、内嵌前端或菜单行为的风险更低。

不采用 rebase，因为当前定制分支已推送，改写历史没有必要。也不采用从标签重建分支后逐个 cherry-pick，因为定制改动跨多个版本积累，容易漏项。

## 合并设计

### 标签合并

在 `codex/update-v0.1.150-custom` 上合并 `v0.1.150`，生成明确的合并提交。合并前保持工作树清洁；现有未跟踪 `.superpowers/` 不加入本次提交。

### 路由冲突

`frontend/src/router/index.ts` 是当前唯一明确的双边修改文件：

- 本地增加了登录后可访问的 `/recharge` 路由。
- 官方 `v0.1.150` 修改了支付和风控路由守卫，使其只在公共设置已成功加载且明确返回 `false` 时禁用功能；公共设置加载失败属于未知状态，不应错误重定向。

合并结果必须同时保留：

- `/recharge` 路由及 `requiresAuth: true`。
- 路由守卫在首次需要支付或风控状态时等待公共设置请求。
- 官方 `publicSettingsLoaded` 判定和显式 `false` 禁用逻辑。
- 公共设置请求失败时不把功能误判为关闭。

### 必须保留的定制行为

- `backend/internal/config/config.go` 和安全头逻辑允许 `frame-src https://pay.ldxp.cn`。
- `backend/internal/service/setting_public.go` 保留自定义菜单归一化及默认项，并兼容官方公共设置字段。
- `frontend/src/components/layout/AppSidebar.vue` 保留 `/recharge` 与自定义菜单显示逻辑。
- 中英文 `common.ts` 保留充值菜单文案。
- `CustomPageView.vue` 保留 iframe token 传递后从可见 URL 移除 token 的行为。
- `ExternalRechargeView.vue` 保留应用内 iframe 与新窗口打开能力。
- `backend/internal/web` 保留定制前端覆盖和内嵌静态资源逻辑。
- CSP 同时保留官方来源、`blob:` 图片支持和定制支付/排行榜 iframe 来源。

## 测试设计

### 测试先行

在修改冲突文件前，先确认或补充能表达合并后行为的测试：

- 路由注册中存在 `/recharge` 且要求登录。
- 首次访问支付路由会等待公共设置请求完成。
- 公共设置明确返回 `payment_enabled: false` 时重定向。
- 公共设置加载失败时不误判为功能关闭。
- 现有侧边栏、充值页、自定义页、CSP 和内嵌资源测试继续通过。

若官方新增测试已覆盖公共设置语义，只补定制路由断言，不复制官方测试。

### 本地验证门槛

至少执行：

1. 后端定制相关单元测试：公共设置、CSP、安全头和内嵌前端。
2. 官方 `v0.1.150` 改动涉及的 service、middleware、repository 和 handler 测试。
3. 后端全量 `go test ./...`；需要外部依赖的集成测试若无法本地运行，必须单独记录，不得以局部测试替代而宣称全量通过。
4. 前端定制相关 Vitest 测试。
5. 前端全量 `pnpm test:run`。
6. 前端 `pnpm typecheck` 与生产构建。
7. 排行榜 `go test ./...`。
8. 主 compose 与排行榜 overlay 的 `docker compose config --quiet`。
9. Linux amd64、`embed` 标签后端二进制构建。

## 构建与制品

前端在本机完成生产构建，后端在本机交叉编译为 Linux amd64 静态二进制，版本元数据使用：

- Version：`0.1.150-ui1`
- Commit：升级分支当前短提交号
- Date：构建时 UTC 时间
- BuildType：`release`

最小 Docker 上下文只包含：

- `Dockerfile.prebuilt-binary` 作为上下文根目录的 `Dockerfile`
- `build-local/sub2api`
- `backend/resources`
- `deploy/docker-entrypoint.sh`

本地归档位于 `deploy-artifacts/sub2api-custom-0.1.150-ui1-context.tar.gz`。服务器只负责解压上下文和执行轻量 `docker build`，避免在资源有限的生产机安装完整前端和 Go 构建链。

## 生产部署

部署前再次确认旧容器健康并记录当前镜像。然后：

1. 上传构建上下文到 `/opt/sub2api-build/sub2api-custom-0.1.150-ui1`。
2. 构建 `sub2api-custom:0.1.150-ui1`。
3. 检查镜像存在并可读取镜像元数据。
4. 给 `/opt/sub2api-deploy/docker-compose.override.yml` 创建带时间戳的 `bak-v0150` 备份。
5. 仅把 override 中的主应用镜像从 `0.1.149-ui1` 改为 `0.1.150-ui1`。
6. 执行带主 compose、override 和排行榜 overlay 的 `up -d sub2api`。
7. 最多等待约 60 秒，直到 `sub2api` 容器报告 `healthy`。

发布过程中不停止或重建 PostgreSQL、Redis 与排行榜。切换会有主应用容器重建所需的短暂连接中断。

## 线上验证

容器健康后依次验证：

- `docker compose ps` 中四个服务状态正常，非主应用容器的创建时间不改变。
- `docker inspect sub2api` 显示目标镜像且健康。
- 本机 `http://127.0.0.1:8080/health` 返回成功。
- 公网 `https://api.zhouz.online/health` 返回成功。
- `/api/v1/settings/public` 返回成功且必要字段存在。
- 首页 CSP 同时包含 `https://pay.ldxp.cn` 和排行榜所需来源。
- 登录页和应用静态资源可加载，没有 5xx 或空白页面。
- 登录后 `/recharge` 可打开，iframe 地址正确，新窗口按钮可用。
- 自定义排行榜页面可打开，token 不残留在可见 URL。
- `http://127.0.0.1:8095/leaderboard/health` 返回成功。
- `GET /api/v1/auth/me` 的 Bearer token 契约未改变。
- `public.usage_logs` 和 `public.users` 中排行榜依赖列仍存在。
- 部署后的主应用日志没有持续 panic、迁移错误、数据库错误或 5xx 激增。

涉及登录态的 UI 验证使用现有浏览器会话；不在日志、文档或提交中保存 token、cookie 或密码。

## 回滚

触发条件包括：

- 主容器无法在等待窗口内健康。
- `/health`、公开设置或首页静态资源失败。
- 定制充值页、排行榜入口或 CSP 丢失。
- 出现持续数据库错误、panic 或关键 API 5xx。

回滚步骤：

1. 恢复本次部署前的 `docker-compose.override.yml.bak-v0150-<timestamp>`，或把镜像明确改回 `sub2api-custom:0.1.149-ui1`。
2. 仅执行 `up -d sub2api`。
3. 等待旧容器健康。
4. 重新验证本机与公网 `/health`、公开设置、CSP、充值页和排行榜。

由于 `v0.1.150` 没有数据库 schema 变更，回滚不需要恢复数据库。失败镜像和构建上下文保留用于排查，不在回滚过程中清理持久化数据。
