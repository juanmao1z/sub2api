# Agent Note: v0.2.19 ARM64 升级与上传部署兼容

Status: implemented

## Problem

升级前主项目与生产基线为 v0.2.17。官方 v0.2.19 提交为 dece26153621959ccd7635814f4b2d08304e681a，源码 VERSION 为 0.2.18，工具链升级至 Go 1.27.3。直接依赖源码版本会构建出错误版本。固定控制台、工单、计费与出站连接安全定制必须保留，适配验证与生产发布分开进行。

## Decision

合并已验证的 v0.2.19 标签后端与必要源码更新，显式构建 0.2.19、目标 linux/arm64。workspace.json 同时保存标签提交、原始 VERSION 与项目版本；production.lastDeployedImage 只在正式上线并通过健康检查后更新。两个 Dockerfile 使用 Go 1.27.3。主 Dockerfile 固定 pnpm 9.15.9，Corepack 引导与依赖安装共用可选 NPM_CONFIG_REGISTRY，保留完整性校验；代理与镜像源仅取当前命令环境。

固定控制台组装输入、画布、指南、渠道健康颜色补丁和出站私网策略继续使用。后端支持新管理员密钥、Grok 诊断和按张计费 API，但固定控制台没有相应新管理入口。支持生图的分组更新省略 image_count_billing 时保留现值，新增字段默认 false。

启动应用时增加迁移 246–248。246 为 Gemini 和 Antigravity 分组（包括软删除分组）开启生图，不处理 composite 分组；247 建立 scoped_admin_api_keys；248 增加分组按张计费开关。历史迁移及自定义 243_support_ticket_system.sql 保持内容和文件名，校验和不重写。应用镜像回滚不恢复数据库 schema 或数据，正式切换前必须准备可恢复的数据库备份。

上传继续验证压缩包 SHA256、镜像 ID、架构、版本与 revision；上传本身不执行迁移。部署继续仅重建 sub2api，保留 PostgreSQL、Redis、leaderboard 及数据。部署回归测试从 workspace.json 读取已验证版本，覆盖官方源码 VERSION 落后于发布标签的情况。正式远端写入拒绝未提交源码和未完成合并。适配验证阶段不执行发布；用户明确要求推送上线后，执行合并提交、正式镜像构建、origin/main 与发布标签推送、数据库备份与恢复校验，再上传并切换应用。发布清单记录每一步和最终远端状态。

## Test isolation and time contracts

从同一 v0.2.19 标签恢复因裁剪而缺失的共享测试依赖，保持新增回归覆盖。高峰计费测试按 timezone.Location() 构造本地 00:30；SQLite 支付租约夹具以 UTC 写入过期时间，避免与生产 UTC 查询阈值进行文本比较时受宿主偏移量影响。两组用例在 UTC 与 Asia/Shanghai 均通过，运行时算法和原断言保持不变。

升级测试创建并清理独立数据库，使用 public schema。历史迁移显式检查 public，单独设置 search_path 不能可靠模拟升级。测试先执行不含 246–248 的完整定制迁移集，写入工单与分组，再执行新增迁移；同时验证历史校验和、记录数、数据保留、开关、新表和重复执行。旧迁移集接受新增 ledger 记录只证明迁移校验兼容，不代表完整旧应用已经通过运行验证。

## Alternatives considered

直接拉取官方镜像可避免本地合并与构建，但会失去工单、前端和连接安全定制，因此继续构建定制镜像。只挑选若干后端补丁可以减小差异，但不能完整保留两个发布之间的修复与迁移，因此采用固定标签合并。

恢复完整官方前端能立即提供新管理入口，但会替换现有控制台且扩大本次部署适配范围，因此保留固定资源并明确功能边界；需要新管理页面时另行评估前端适配。

单一 UTC 测试环境可以绕过夹具时区问题，但会掩盖上海时区开发环境中的误报，因此修正夹具并保留双时区验证。单独 schema 的数据库隔离更轻量，但历史 SQL 对 public 的显式检查使它不等价于真实安装，因此使用临时数据库，不修改历史 SQL。

## Consequences

固定标签、显式版本和产物摘要使源码与验证镜像可核对；固定控制台继续保留现有定制，新增官方管理 UI 需要后续适配。恢复上游共享测试会增加仓库测试体积，但避免通过删除新回归测试来绕过编译依赖。

未发现新增强制生产环境变量。Gemini 同账号重试默认 4、范围 0–10；数据库、Redis、JWT 和加密配置继续沿用现有要求。笔记门禁通过仓库根 package.json 的 npm run verify-notes 调用工作区已安装的技能脚本，执行时需要 Node/npm 和该工作区技能目录。

合并冲突均已解决。带 -dirty 的适配镜像只用于本地验证；正式上传须使用已提交合并和发布标签，重建绑定清洁 revision 的镜像。上线前在生产服务器受限目录保存 PostgreSQL custom-format 备份并计算摘要，恢复到独立临时数据库检查后删除该临时数据库，备份本身保留。仅重建应用服务，随后核验容器健康、公网 /health、新迁移账本和保留服务 ID。正式产物、备份及结果证据写入 deploy-artifacts/<release>/release.json；应用镜像自动回滚不能替代数据恢复。
